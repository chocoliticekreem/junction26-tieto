# REQ-2283: Generator and analyzer crash with IndexOutOfRangeException on a closed generic struct from a referenced assembly

Source: https://github.com/MessagePack-CSharp/MessagePack-CSharp/issues/2283
Type: bug

## Requirement

Both `MessagePackGenerator` (CS8785) and `MsgPack00xMessagePackAnalyzer` (AD0001) throw `IndexOutOfRangeException` when a `[MessagePackObject]` type has a member whose type is a closed generic value type defined in a referenced assembly.

Because the generator then "will not contribute to the output", the compiling assembly silently ends up with no generated resolver at all. It is only a warning, so a normal build looks fine, but trimmed and NativeAOT apps fail at runtime.

Repro: two projects. `lib`:

```csharp
using MessagePack;
namespace Lib;

[MessagePackObject]
public partial record struct Item<T>([property: Key(0)] string Key);
```

`app`, with a `ProjectReference` to `lib`:

```csharp
using MessagePack; using Lib;
namespace App;

[MessagePackObject]
public sealed partial record Cmd([property: Key(0)] string Scope)
{
    [Key(1)] public Item<int> Member { get; init; }
}
```

Then `dotnet build` on `app`.

Expected: a clean build, with a generated resolver in `app`.

Actual:

```
CSC : warning CS8785: Generator 'MessagePackGenerator' failed to generate source. It will not
contribute to the output and compilation errors may occur as a result. Exception was of type
'IndexOutOfRangeException' with message 'Index was outside the bounds of the array.'.
CSC : warning AD0001: Analyzer 'MessagePack.SourceGenerator.Analyzers.MsgPack00xMessagePackAnalyzer'
threw an exception of type 'System.IndexOutOfRangeException' with message 'Index was outside the
bounds of the array.'.
```

`app.dll` contains no `GeneratedMessagePackResolver`. Version used: MessagePack 3.1.8.

What triggers it (`Item` declared in `lib`, `Cmd` in `app`):

| `Item` declared as | result |
|---|---|
| `record struct Item<T>` | crash |
| `struct Item<T>` | crash |
| `struct Item` | ok |
| `record struct Item` | ok |
| `class Item<T>` | ok |
| `record class Item<T>` | ok |

It needs all three of: generic, value type, from a referenced assembly. Moving the identical `Item<T>` declaration into `app` makes the crash disappear.

Reporter's analysis: `CollectGeneric` line 661 is the closed-generic branch that calls `GetObjectInfo` directly, so `GetObjectInfo` runs against a type that has no syntax. Several diagnostic paths inside it index `DeclaringSyntaxReferences[0]` directly (lines 735, 1009, 1101) instead of using `FirstOrDefault()` like the neighbouring `GetIdentifierLocation` / `GetLocation` / `GetParameterListLocation` helpers. That collection is empty for a metadata symbol. The reporter did not narrow down which of the three fires.

Workaround: `[MessagePackFormatter(typeof(ItemFormatter<>))]` on the generic value type short-circuits `CollectCore` before `GetObjectInfo` is reached.

## Acceptance criteria

- Building `app` from the repro produces no CS8785 warning. (derived)
- Building `app` from the repro produces no AD0001 warning from `MsgPack00xMessagePackAnalyzer`. (derived)
- `app.dll` contains a `GeneratedMessagePackResolver` (a generated resolver exists). (derived)
- The generator and analyzer do not throw on a closed generic struct or record struct declared in a referenced assembly.
- Closed generic classes, non-generic structs and types declared in the same assembly keep working as before (the "ok" rows in the table). (derived)
- Diagnostics that need a source location do not crash when the offending symbol has no declaring syntax (metadata symbol). (derived)

## Notes from discussion

No comments on the issue. The reporter points at `DeclaringSyntaxReferences[0]` being indexed unguarded at TypeCollector.cs lines 735, 1009 and 1101, and notes the neighbouring helpers use `FirstOrDefault()`. Possibly related: #2092 (CS8785 from the v3 generator, different inner exception, no repro).
