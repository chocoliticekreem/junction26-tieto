# REQ-2129: Feature Request: Allow generation of Formatter for a type in a referenced assembly

Source: https://github.com/MessagePack-CSharp/MessagePack-CSharp/issues/2129
Type: feature

## Requirement

Given Project A (contains `ProjectA.MyType`, has no and cannot have a reference to the MessagePack NuGet package) and Project B (references Project A and MessagePack), the reporter needs a source-generated `IMessagePackFormatter` for `ProjectA.MyType` generated inside Project B.

Proposed solution: add a `[GeneratedMessagePackFormatter]` attribute that works for partial classes implementing `IMessagePackFormatter<T>`:

```csharp
[GeneratedMessagePackFormatter]
partial class MyObjectFormatter: IMessagePackFormatter<MyObject>;
```

The class does not need a body; the implementation is source-generated by `MessagePack.SourceGenerator.MessagePackGenerator` as usual.

For attribute-based property keys and other settings (such as Union), the issue lists three alternatives: (1) use `System.Runtime.Serialization.DataMember` and related attributes; (2) let the generator and analyzers work with user-defined copies of the MessagePack attributes; (3) source-generate the attributes themselves via `RegisterPostInitializationOutput`.

Motivation: Project A is a NuGet library that should stay minimal with zero dependencies.

## Acceptance criteria

- A `[GeneratedMessagePackFormatter]` attribute exists and can be applied to a partial class implementing `IMessagePackFormatter<T>`.
- The source generator emits the formatter implementation for `T` inside the annotated class, in the assembly that declares the class (Project B), even when `T` is declared in a referenced assembly.
- The annotated class may be declared without a body (`partial class X : IMessagePackFormatter<T>;`).
- `T` needs no MessagePack attributes: without `[DataContract]` or `[MessagePackObject]` on `T` the generated formatter uses contractless behaviour over public members. (derived from maintainer comment)
- If `T` does carry MessagePack attributes, they are honoured. (derived from maintainer comment)
- Private members are not required to be serialized; only public members are in scope. (derived from maintainer comment)
- Project A needs no reference to the MessagePack package. (derived)

## Notes from discussion

- AArnott: "We might simplistically say this only works in 'contractless' mode, such that you need no attributes on it at all. If there are attributes on it, fine, we'll use them. But if there is no `[DataContract]` or `[MessagePackObject]` attribute on the type, go contractless by default."
- AArnott on prerequisite: "Does ProjectA.MyType requires only `public` members to be serialized? That seems a prerequisite for anything here." Reporter: yes.
- AArnott is not a fan of a `PropertyKeys` dictionary on the formatter, and warns that copying attributes into Project A breaks reflection-based (dynamic resolver) mode.
- AArnott suggested a surrogate-type design: `[GeneratedMessagePackFormatter(SurrogateType = typeof(ProjectASurrogate))]`, keys mapped by property name; reporter: "Looks good." No design was settled in the thread.
