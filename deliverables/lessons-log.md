# Lessons log

Failure modes we actually saw while building and running PullReceipts, and what each one changed. Newest last.

## Failure modes in the AI-written changes under review

1. **The agent's change to #2283 is wider than the requirement.** Same root cause as the human-written upstream PR #2305 (`DeclaringSyntaxReferences[0]` on a metadata symbol), but it also adds a filter that drops every diagnostic located outside the compilation. Two consequences a reviewer must see: diagnostics for types declared in the project itself with no source location are dropped too (flagged independently by several lenses), and a null key on a positional record parameter is no longer reported. Lesson: compare an agent change with the requirement's scope, not only with "does it fix the bug".
2. **The agent's tests for #2283 pass with the diagnostic reporting removed.** Mutation testing produced 4 surviving mutants out of 6 on `TypeCollector.cs` (deleting `report(diagnostic)`, negating `is null`). The tests prove "no crash", not "still reports". Lesson: a green test suite written by the same agent is weak evidence; mutants measure its teeth.
3. **The agent's #2297 change fences the attribute off with `#if !NETSTANDARD2_0 && !NETFRAMEWORK`.** `ExcludeFromCodeCoverageAttribute` exists on both, so those users keep generated code in coverage reports despite "all generated code". That one is a code reading (both targets ship the attribute); it stays a hunch until a build on those targets proves it. A logic-edge test did produce an executed receipt: CS0579 (duplicate `ExcludeFromCodeCoverage`) on head when user code already carries the attribute.
4. **#2297 is ambiguous and the agent picked silently.** The issue says "I do not feel like a setting is needed, but setting would be fine to have too". The reviewer refuses to pick and produces two branches instead.

## Failure modes in our own reviewer

5. **A context-free lens wants to "fix" a deliberate convention.** The generator deliberately skips types it only sees as metadata (`TypeCollector.cs` `IsInMetadata` early return). Without the ledger entry, that looks like a missing diagnostic. With it, the product-context lens cites the entry instead of flagging. This is the "generic error message" problem from the brief, found in this codebase.
6. **LLM-written tests fail for the wrong reason.** First drafts failed because the project's snapshot verifier had no snapshot file, or because `AnalyzerOptions` was ambiguous (CS0104) with a type in the project's global usings. A test that fails on base is only evidence if it fails for the requirement's reason, so the check records the failure message and the lens prompt now carries these traps.
7. **A logic-edge hunch was refuted by its own test.** On 2283 the logic-edge lens wrote an edge-case test it expected to fail on head; it passed. The receipt killed the hunch. This is the system working: suspicion goes in, only executed results come out as findings.
8. **A sample set can be too narrow.** The byte-diff harness first missed a planted change in the `short` writer because no case covered `short -128`. Fixed by repeating boundaries for every integer type (124 cases). Lesson: "byte diff passed" is only as strong as the sample set, so the receipt lists the cases.
9. **A silent import fallback hid a router.** The router registry skips modules that fail to import, and one entry pointed at the wrong module name, so the LLM router would have been silently skipped. Caught in integration by asserting the registry contents. Lesson: fallbacks must be visible in the receipt (the routing report now names the router that actually ran).
10. **Wall-clock claims need a clock.** The orchestrating agent wrote progress times from estimate rather than `date`, and had to correct them from git commit times. Same rule as findings: no receipt, no claim.
11. **Our first verification was too loose.** An adversarial reviewer, given only the spec and the code, showed that a finding could be "verified" by evidence unrelated to its claim: a security claim by any failing byte diff, a README claim by an unrelated failing test. "Backed by a receipt" has to mean backed by *its own* receipt. Verification now requires the artifact to name the claim (the failing test by name, the byte diff traced to the finding's file). Lesson: run an independent adversarial pass on the trust mechanism itself, not only on the code under review.
12. **Ambiguity detection flipped on prompt wording.** Hardening the lens prompts against injection changed their text, and on the fresh calls REQ-2234 went from "two readings, A/B" to "no ambiguity". A trust decision that flips on wording is not a trust decision, so ambiguity is now a vote of three independent readers that see only the requirement.
13. **API keys sat in the environment of untrusted builds.** `dotnet build` of an agent-written change runs that change's MSBuild code. Subprocesses that run repo code now get an allowlisted environment. Any reviewer that executes code under review is itself an attack surface.
14. **A surviving mutant needs a scope.** Our mutator ran only the change's own tests, and 4 of 6 mutants on 2283 survived them. Stryker.NET, run as a cross-check, agreed on every mutant both tools made, but the full suite killed all 6 of ours, and Stryker found 2 survivors of the full suite that we never generated (`&&` to `||`, `FirstOrDefault()` to `First()`). Our receipt was true but worded too broadly. Survivors are now re-run against the full suite, and only full-suite survivors are reported as test gaps. Lesson: cross-check a home-grown receipt generator against an established tool before trusting its numbers.
15. **We were reviewing the feature, not the product.** In a live review of our demo, a Tieto engineer said finding that the new feature is wrong is good, but what a reviewer really fears is the change that does the new thing right and breaks an old thing: an existing function, used in many places, modified for the new feature. With legacy code, test coverage is never complete and full regression after every change does not scale. Our lenses judged the change against its ticket; none looked at who else calls the changed code, and the router only saw one hunk at a time. Lesson: requirement-driven review answers "does it do what was asked"; trust also needs "what else did it touch", made concrete as callers, coverage and pinned old behaviour.
16. **Name-based call sites over-count.** The first blast-radius run matched callers by name on syntax trees. On 2129, 11 of the 14 callers outside the change were `.Equals(` calls, most on other types (Unity `Color.Equals`, a runtime resolver); one was real: `Comparer.Equals` in `MessagePackGenerator.cs:156`, untested. Lesson: a call-site count without a semantic model is an upper bound; the receipt marks it `ambiguous` and names the method, so the human sees which caller matters.
17. **The batch run exposed a leak in our old cold baseline.** Re-running the bench through the Message Batches API built every cold prompt against the empty ledger at once. The PR #11 "cold" run had not: cases that finished early wrote oracle answers that later cases saw (39 ledger citations in a run meant to be cold). The truly cold figure is 0.81 questions per change (29 on 36 cases), not 0.25. Lesson: a baseline measured while it learns is not a baseline; isolate the state each case can see.
18. **Our questions tile compared unequal case sets.** The dashboard first showed 0.81 to 0.28: 36 cold cases against 18 warm ones. On the same 18 cases it is 0.50 to 0.28 (9 to 5), and the ledger helped one issue (2234: 7 to 0) and not the other (2283: 2 to 5). Warm runs also cited the ledger 0 times: the bait false alarms stayed at 3 and 5. Lesson: a before/after number is only honest on the same cases, and the ledger's effect is smaller than lesson 5 suggested.
19. **An open-weight model's tests compile but rarely prove anything.** On Verda, Kimi K3.1 Pro's generated tests compiled 55 of 77 times on the bench, but only 6 of 77 behaved as their plan said (Opus: 34 of 93). Its A/B builder produced a working second reading on 1 of 3 ambiguous changes. It caught 18 of 24 plants against 21, with the same 0 escapes. Lesson: because every finding needs its own receipt, a weaker model shows up as more "not checked" and fewer verified findings, not as false greens. The test-writing lenses are where model quality pays.
